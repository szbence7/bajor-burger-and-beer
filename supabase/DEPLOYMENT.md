## Initial transfer

Before modifying the destination, full database backups of the local project,
destination and Coolify configuration were taken, plus a local Storage volume
archive. The local backup copies are in `.backups.local/20261103/` at the repository
root (git-ignored, private). Destination backups are in
`/data/bajor-transfer-20261103/` on the server (root-only).

Migrations 0001–0009 were executed, followed by the actual `public` table data,
`auth.users`, `auth.identities`, `auth.mfa_factors` and migration history in one
transaction. The Auth table structures were checked for compatibility first.
Postgres 17-only dump settings and psql restriction directives were omitted for
the destination's Postgres 15 tools. Internal Auth/Storage schemas and local JWT
secrets were not restored over the destination's managed schemas or keys.

The 9 Storage files were copied through the Storage APIs into the destination's
S3-backed storage. Source and public destination downloads matched by SHA-256.
Storage object versions and metadata are generated by the destination upload;
this was a file transfer, not a restore of the local filesystem storage backend.

Transferred content: 3 menu categories, 18 menu items, 8 beers, 9 gallery entries,
7 monthly specials, 4 opening-hour rows, 1 settings row, 1 Auth user and 1 verified
TOTP factor. Reservations and notification logs were empty. Existing password
hashes, user IDs, admin metadata and the TOTP secret were preserved. Users must
sign in on the new origin; old local sessions were not copied.

## Remaining configuration

SMTP is not configured in the production webapp or Supabase Auth. Booking and
account emails require a real SMTP provider; local Mailpit settings were not
copied to production.

The saved backups are migration snapshots, not a recurring backup schedule.
Future backups must cover both Postgres and the S3/MinIO Storage objects.

For later schema changes, use the migration history and apply only unapplied
migrations. Avoid the initial bootstrap script, `db reset`, and `db:push`'s
`--include-seed` option when the intention is to preserve production content
without inserting launch seed rows. Use an SSH tunnel for database access.
