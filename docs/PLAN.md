## Original master prompt (verbatim)

> The user's original brief, unchanged. Where later decisions differ, the
> "Decisions and deviations" section below takes precedence.

````markdown
# Project: Bajor Burger and Beer website (bajorburgerandbeer.hu)

## Context
This repo was generated by Lovable as a design-first build for "Bajor Burger and Beer", a modern burger and craft beer house in Budapest. I am now continuing development with you. The design direction is approved and must be preserved; your job is to fix the design issues, then turn it into a production-ready app.

Before changing anything:
1. Explore the repo and summarise the current stack, folder structure, routing, components, mock data and image handling.
2. Create a CLAUDE.md in the repo root that captures the project context, design system and conventions from this prompt, so future sessions stay consistent.
3. Work on a new branch (`claude/redesign-fixes`), not on main.
4. Work in phases. After each phase: run the build and lint, summarise what changed, and STOP for my review before continuing.

## Language and content rules
- All visible UI text is in Hungarian. Code, comments and commit messages in English.
- Prices in Ft, Hungarian number formatting (e.g. 4 290 Ft, 0,5 l, 5,3%).
- Keep the existing images; they are good. Images will later be replaced with the restaurant's own photos, so keep image paths centralised and easy to swap.

## Design system (keep it, enforce it everywhere)
- Feel: a hybrid of a moody evening burger and beer house and a bold, playful, youthful street-food brand. Dark and atmospheric base, loud graphic moments on top. Must never look like a generic restaurant template.
- Colours (as Tailwind theme tokens, no hardcoded hex in components):
  - Background #121110, surface #1C1A18, border #2E2A26
  - Primary cheddar gold #F2A900, tint #FFC94A
  - Accent ember red #D9381E, only for main CTAs and badges
  - Text #F5EFE6, muted #A89F94
- Typography: ultra-heavy condensed display font for oversized headlines, clean sans (Manrope) for body.
- Signature elements: tilted infinite marquee strips (gold, dark uppercase text, small burger/beer icons), cut-out burgers overlapping giant type with a warm golden glow, hand-drawn line doodles (burger, beer mug, pretzel, fries, hop cone), one or two full-width gold sections, giant "BAJOR" wordmark in the footer.
- Motion: scroll-reveal, marquee, hover lift with gold glow, slight parallax on the hero burger. Respect prefers-reduced-motion.

## PHASE 1: Design fixes
1. Hero: the burger is too large. It covers "CSAPOLT SÖR." so the main slogan is unreadable, and it overlaps the header, hiding the nav links. Resize and reposition it so both headline lines stay fully legible and the header is never covered. The burger may overlap the headline slightly as a stylistic touch, but never hide whole words. Check at 375, 768, 1280 and 1920 px widths.
2. Featured burger cards: the second line of each name ("BAJOR DUPLA", "POKOL TÜZE", "ZÖLD PERECES") is hidden by the burger image. Keep the overlap idea, but the full name must always be readable (e.g. text above the image layer, smaller burger, or burger anchored lower).
3. Background pattern: the current pattern renders as a broken, pixelated, staircase-like checkerboard. Remove it everywhere.
   - Hero: no pattern. Dark background, warm golden radial glow behind the burger, subtle grain overlay.
   - Recreate the Bavarian diamond (Rautenmuster) as a clean SVG pattern of proper 45-degree rotated diamonds at 3 to 5% opacity. Use it only in the footer and on the map card, optionally as a thin decorative divider strip between sections.
4. Doodles: raise their opacity to about 10% so they add texture to the dark sections, which currently feel a bit empty.
5. Beer cards: text is too small. Increase the size of style, brewery, ABV and especially prices; make sure contrast meets WCAG AA.
6. Gallery strip ("A HELY"): currently a flat row. Make it a horizontal carousel of rounded-3xl photo cards with slight alternating rotations (-2deg / 2deg), straightening on hover.
7. Full responsive pass on every page, especially mobile: no horizontal scroll, no clipped headlines, readable marquees, usable booking form.
8. Check every subpage (Menü, Galéria, Asztalfoglalás, Rólunk & Kapcsolat, 404) for the same issues and for consistency with the homepage.

## PHASE 2: Migrate to TanStack
- Migrate routing to TanStack Router (file-based routes) with Vite, keeping the current React + TypeScript + Tailwind setup and all components. Use TanStack Query for data fetching.
- Keep the app as a static SPA build suitable for deployment on my Coolify VPS (Git-based auto-deploy). Add a Dockerfile or Nixpacks-compatible config and SPA fallback routing.
- Remove Lovable-specific leftovers that are no longer needed (e.g. lovable-tagger), but do not break the build.
- Clean up structure: /src/routes, /src/components, /src/features (menu, booking, gallery), /src/lib, /src/data.
- Add per-page SEO: titles, meta descriptions, Open Graph tags, favicon, and Restaurant JSON-LD structured data (address, opening hours, menu URL, acceptsReservations).

## PHASE 3: Supabase backend
I host Supabase on my Coolify VPS. Use environment variables for the URL and anon key (.env.example, never commit secrets).
- Replace the mock data in /src/data with Supabase tables, keeping the same TypeScript types:
  - menu_categories, menu_items (burgers, sides, other drinks: name, description, ingredients, price, image, badges, sort order, is_active)
  - beers (name, style, brewery, ABV, tap or bottle, size/price options, image, is_active)
  - gallery_images (url, category: hely / ételek / sörök / események, sort order)
  - opening_hours, site_settings (address, phone, email, socials)
  - reservations (date, time slot, party size, name, phone, email, note, status: pending / confirmed / cancelled, created_at)
- Write SQL migrations and a seed script that loads the current mock content.
- Row Level Security: public can read active menu, beers, gallery and settings; public can only INSERT reservations (no reading other people's bookings); admin role has full access.
- Booking: validate with zod; only offer time slots within opening hours; block past dates; show a clear confirmation screen. Leave a clean hook point for email notifications (to be added later).

## PHASE 4: Admin panel
A protected /admin area (Supabase Auth, email + password, admin role only) in the same design language, but calmer and practical:
- Reservations: list and calendar/day view, filter by date and status, confirm or cancel.
- Menu and beers: create, edit, reorder, toggle active, upload images to Supabase Storage.
- Gallery: upload, categorise, reorder, delete.
- Opening hours and contact details editing.
Hungarian UI, mobile-friendly (the staff will use it on phones).

## Quality bar
- No regressions in the visual design; compare against the current homepage after each phase.
- Lighthouse: aim for 90+ on performance, accessibility and SEO. Lazy-load and properly size images (WebP/AVIF where possible).
- Small, focused commits with clear messages.

Start with the repo exploration and CLAUDE.md, then Phase 1.
````

## Decisions and deviations

Agreed with the user during Phases 1–2. These override the original prompt where they differ.

1. **Phase 2 kept TanStack Start SSR on a Node server instead of a static SPA.** The repo was
   already TanStack Start (SSR) + TanStack Router + Query, not a plain React Router app. SSR
   was kept because server-rendered titles, Open Graph tags and JSON-LD matter for SEO and
   link previews. The `@lovable.dev/vite-tanstack-config` wrapper was replaced by a plain
   Vite config; Nitro builds a `node-server` bundle (`.output/server/index.mjs`) instead of a
   Cloudflare worker. There is no SPA fallback because every route is server-rendered.
2. **Docker for Coolify.** Multi-stage `Dockerfile`: bun builds, `node:22-alpine` runs only
   `.output/` as the `node` user, listens on `PORT` (default 3000), `HEALTHCHECK` on
   `GET /api/health`. Coolify: Dockerfile build pack, `VITE_SITE_URL` as a build variable.
3. **Image pipeline.** All images enter through `src/data/images.ts` with `vite-imagetools`
   queries that emit AVIF + WebP in several widths at build time; rendered with `<Picture>`
   and `sizes`. The burger PNGs went from ~1.7 MB to 20–50 kB (AVIF). `ImageSource` also
   accepts plain URLs for Supabase Storage images later.
4. **NOINDEX flag.** Runtime env var (`1`/`true`/`yes`): adds
   `<meta name="robots" content="noindex">` to every page and makes `/robots.txt` return
   `Disallow: /`. For the staging deploy while placeholder contact data is in the JSON-LD.
   Toggle in Coolify without a rebuild.
5. **Doodles at 10% opacity**, used large (`h-28`–`h-56`) as texture in dark sections. (They
   were 25% originally; the user confirmed 10% with larger sizes.)
6. **Rautenmuster divider strip at 12% opacity** (the pattern itself stays 4–5%; a thin strip
   at 3–5% would be invisible). User approved.
7. **Push at the end of every phase without asking**, then stop for the user's review.
8. Other changes beyond the original prompt, all reviewed with the user:
   - shadcn/ui (unused) and ~38 related dependencies removed.
   - Fonts self-hosted via Fontsource (Anton, Manrope); gzip middleware for SSR responses;
     white text on ember for AA contrast; ember never used as a text colour on dark.
   - `font-display` line pitch 1.12 so Hungarian accents don't collide; the hero keeps 0.94.
   - Prices always grouped as `4 290 Ft` via `<Price>` (the hu-HU locale doesn't group
     4-digit numbers).
   - Brand favicon set, web manifest, 1200×630 OG image, `sitemap.xml` server route.
   - Opening hours stored as structured data (weekdays, opens, closes) so the UI and the
     JSON-LD share one source.

### Phase 3 decisions (agreed 2026-10-18, before implementation)

9. **Supabase instance**: a fresh self-hosted instance dedicated to Bajor; no separate staging
   database. Migrations are numbered SQL files in `supabase/migrations` and are tested against
   a local Supabase stack in Docker before they touch the real instance (either applied over
   an SSH-tunnelled `SUPABASE_DB_URL` or pasted into Studio by the user).
10. **Server-side data access.** `SUPABASE_URL` and `SUPABASE_ANON_KEY` are **runtime** env
    vars read on the server (no rebuild to change them). Pages load data in route loaders via
    server functions, so HTML, OG and JSON-LD stay server-rendered; the browser never talks to
    Supabase in Phase 3. Phase 4 exposes URL + anon key to the client for Auth.
11. **Admin role** = `app_metadata.role = 'admin'` on a Supabase Auth user, checked in RLS.
12. **Images in the DB** are either a key of a bundled image in `src/data/images.ts` (keeps the
    AVIF/WebP pipeline) or a plain URL (Supabase Storage uploads in Phase 4).
13. **Placeholder contact data** moves into `site_settings` unchanged; `NOINDEX` stays on.
14. **Booking rules** (all stored in `site_settings`, editable by the admin in Phase 4):
    - slot length 30 min, starting at opening time; a booking must end by closing time;
    - dining duration 90 min: a booking occupies its table for that long (snapshotted on the
      reservation, so later setting changes don't move existing bookings);
    - capacity 40 guests, counted over **overlapping** bookings: a new booking is accepted only
      if every overlapping 30-minute window stays at or under 40 guests (pending + confirmed);
    - party size 1–8 online; above 8 the form shows "call us" (fixes the old 1–10 vs "8 fő
      felett" mismatch);
    - bookable up to 60 days ahead, at least 2 hours' notice; all dates in Europe/Budapest.
    - The rules are enforced in Postgres (trigger + availability function), so they hold for
      every insert path; the UI only offers slots the database reports as available.
15. **Email notifications**: `onReservationCreated()` hook, empty for now.
16. **GDPR**: required consent checkbox linking to a placeholder `/adatkezeles` privacy page
    (final text from the user); the consent timestamp is stored with the reservation;
    reservations older than 12 months are deleted daily by pg_cron, or by a documented SQL
    function when pg_cron is unavailable.
17. **Spam protection**: honeypot field on the booking form and a rate limit of 5 booking
    attempts per IP per hour on the booking server function.

### Brand update (2026-10-21, between Phases 3 and 4)

19. **Primary gold = the logo's gold**: #F2A900 / #FFC94A → #D2AC66 / #E6C88A (8.8:1 on the

    600, Anton only for the home hero, the footer wordmark and 404.
21. **Real photos** come from the restaurant as original files (Facebook can't be scraped and
    serves compressed copies). Until then the AI stand-ins stay.

### Phase 4 decisions (user request, 2026-11-02)

22. **Narrowed scope** (user: "egyelőre más nem kell"): the admin panel covers only
    - **live reservations**: see new bookings instantly, accept or reject them;
    - **PDF menu**: upload / replace the downloadable menu;
    - **Hónap ajánlata**: the home section formerly "Kedvenc burgereink", renamed and made
      editable (own `monthly_specials` table, independent of the menu);
    - **email notification log**, visible to the staff, showing whether each email went out;
    - **mandatory 2FA** for every admin.
    Menu/beer/gallery editing, opening hours and contact details are **not** in this phase.
23. **2FA = TOTP authenticator app** (Supabase Auth MFA). `is_admin()` requires
    `app_metadata.role = 'admin'` **and** `aal2`, so RLS enforces it everywhere (tables,
    Storage, Realtime). Sign-ups are off; admins are invited from the panel (decision 28).
24. **Statuses**: `pending` → `confirmed` / `rejected`; `confirmed` → `cancelled`; a mistaken
    rejection/cancellation can be confirmed again. Only pending + confirmed hold seats. Each
    decision emails the guest, with an optional message from the staff.
25. **Emails over SMTP** (nodemailer, any provider, runtime `SMTP_*` vars): receipt to the guest
    and an alert to the staff on a new booking; a guest email on every decision. Every attempt
    is logged in `notification_log` (sent / failed / skipped) and can be re-sent from the panel.
    Without SMTP settings nothing is sent and the log says so.
26. **Admin architecture**: `/admin` renders client-side only (`ssr: false`, noindex); the
    browser uses supabase-js for Auth, Realtime, Storage uploads and reads; writes go through
    server functions with the admin's token (RLS decides) so the server can send email and
    clear the content cache. The service role key is used only for the notification log.
27. **PDF menu** at the stable address `/etlap.pdf` (good for table QR codes), streamed from
    the public `menu` bucket; the Menü page shows an "Étlap PDF-ben" button once one exists.
    The HTML menu page stays as it is.
28. **Admin accounts from the panel** (user request, 2026-11-02): no self-registration; an
    admin invites a colleague by email, who receives a temporary password, must enter it again and
    set their own password (twice) on first sign-in, then set up 2FA. `is_admin()` ignores accounts still on the
    temporary password. Admins can also reset (new temporary password + 2FA removed) and
    remove other admins; never themselves, never the last admin.

29. **Booking form order** (user request, 2026-11-02): an always-open month calendar (current
    month, closed and out-of-range days disabled) → the day's time slots below → party size
    below that (1…max). The "N fő felett hívj minket" branch is removed.
30. **Adatok page** (user request, 2026-11-02): one admin page for everything the site shows
    about the business: restaurant name, phone, email, address, company name, registered
    office, tax number, company registration number, social links, opening hours (edited per
    weekday, stored grouped) and booking rules. Every page reads them from the database; the
    footer gains an impresszum line. SEO titles keep the brand name in code.

31. **Map** (user request, 2026-11-02): Google Maps embed of the address set in Adatok,
    loaded on click (GDPR: it sends data to Google; also keeps the pages fast), remembered
    in localStorage, plus an "Útvonaltervezés" link. Mention Google Maps in the privacy notice.
32. **Re-accepting** a rejected/cancelled booking is labelled "Mégis elfogadom" (outline, not
    the gold primary button), explains that the guest already got the rejection email, and
    warns when the time window would go over capacity.

### One-page site, PDF menu viewer and fonts (user request, 2026-11-02)

33. **One page.** The public site is a single page with sections (hero, Hónap ajánlata, Étlap,
    Rólunk + Értékeink, A hely, Asztalfoglalás, Kapcsolat); the header links to them as
    `/#id`. No separate gallery ("csak a főoldalon pár kedvcsináló kép") and no HTML menu page.
    `/menu`, `/galeria`, `/rolunk`, `/foglalas` answer 301 to their section; `/adatkezeles`
    stays a page. Sitemap: `/` and `/adatkezeles`.
34. **The menu is the uploaded PDF**, shown in the Étlap section as a real booklet with
    curling pages (user request 2026-11-03: "mint egy rendes füzet"; StPageFlip, `page-flip`):
    one page on phones, an open booklet with the first page as its cover on wider screens;
    drag, swipe, click, arrow keys and buttons; "Nagyítás" shows every page full width
    (pinch-zoom on phones). No download button (user decision); `/etlap.pdf` stays for QR
    codes. The admin panel renders the pages to WebP with pdf.js when the PDF is uploaded
    (migration 0008), so visitors get plain images and no PDF renderer; each page's text goes
    to screen readers. The section and its nav link are hidden until a menu is uploaded.
    `menu_items`, `beers`, `gallery_images` are no longer read by the site (tables kept).
35. **Fonts from the restaurant's printed menu**: body text in **Share** (Google Fonts; a near
    exact match of the menu's squarish condensed sans), accent in **Norican** (closest free
    match of the menu's brush script, which is probably a commercial font). Norican always
    sets the Hónap ajánlata dish names, otherwise only a word in a headline. Headlines stay
    Oswald, the hero/footer/404 stay Anton.

### Most csapon (user request, 2026-11-03)

36. **Most csapon** section after the menu: a row of gold beer taps, as many taps as beers on
    tap, each beer's round logo on its handle; only the logos show (the name is alt text and
    tooltip). Own `taps` table (migration 0009: name, logo URL, order, is_active; public reads
    active rows, 2FA admins manage), edited in admin → Most csapon (logo upload to `media`,
    reorder, take off / back on tap, delete). Hidden when no tap is active.
